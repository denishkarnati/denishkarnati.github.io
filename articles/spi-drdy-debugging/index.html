ADC / SPI / BENCH DEBUGGING

Debugging SPI and DRDY timing

Separate converter timing, SPI framing, and host decoding with a repeatable capture.

Technical guide · Dinesh Karnati · October 2026

Start with a testable symptom

A missing sample, a repeated word, and a clipped waveform are different failures. Record the input condition, expected sequence, and where observed data diverges. Keep the firmware revision and converter configuration with the capture.

The ADS131M04 is a four-channel, 24-bit converter with an SPI interface and a data-ready signal. Its datasheet defines frame structure and timing. Those definitions establish what a capture must show; a familiar-looking plot does not prove that the interface is correct.

Capture the boundary before the plot

Probe DRDY, chip select, SCLK, and data output together. Record analyzer sample rate and decode settings. Measure the delay from data-ready to the first clock and the duration of a complete transfer. Compare the transaction with the configured frame format.

Keep raw received bytes beside decoded channel values. A correct bus transaction can still be misinterpreted through byte order, word alignment, or signed conversion. Use a known stimulus and change one timing or decoding variable per test.

Follow the evidence

If DRDY arrives without a transfer, inspect interrupt handling, scheduling, and bus ownership. If a transfer is incomplete, inspect word length, frame length, and transaction completion. If raw values are stable but decoded values jump, inspect sign extension, channel offsets, scaling, and host parsing.

These are hypotheses to test. Repeated values may be legitimate for a steady input. The stimulus and capture must distinguish that possibility. Avoid changing both the stimulus and firmware in the same comparison.

Close the loop with a regression

Repeat the original failing condition after a change, then vary acquisition rate and communication load. Count acquisition events, completed transfers, and accepted host samples independently. Save the raw capture and a decoding example so another engineer can repeat the check.

A useful bug report pairs a symptom with a boundary capture and a reproducible test. This guide describes a method, not an unpublished board result.
