01

The project

I developed an IoT patient-monitoring project around BeagleBone Black and a Yocto Linux platform. The system integrated MAX30100 and LM35 sensors and used MQTT for a connected data path. The project brought together sensor interfaces, embedded Linux, and host-to-network communication.

This project connects an embedded Linux target to both the physical sensing environment and a network. Those two interfaces give it a useful systems perspective: data has to enter the target consistently before it can become a useful message elsewhere.

02

The engineering boundaries

The architecture can be understood as four boundaries: a physical signal becomes a sensor reading, the reading enters the Linux system, software prepares it for transport, and the network carries it to a consumer. Keeping those boundaries visible makes it easier to explain where the embedded work sits.

The implementation combines sensing hardware, a Yocto-based target, and MQTT communication. Its value as an independent engineering project is the integration across these layers and the ability to follow a reading from its origin to its connected representation.

03

A useful way to reason about reliability

Network availability and acquisition availability should be considered separately when explaining a connected sensing system. If a link drops, a useful question is what happens to newly produced samples. Another is how a receiving application distinguishes a new message from one that was held locally.

The walkthrough below isolates those questions with a small browser model. A visible local buffer and separate delivery counter make one possible reconnection policy concrete, so the consequences of changing link state can be examined directly.

04

Try the communication workflow

Send a synthetic sample while MQTT is connected, then disconnect the broker and send a few more. The generated, buffered, and delivered counters make the state changes explicit. Reconnect to transfer the buffered messages.

Each synthetic sample has an identifier and a readable payload. Follow those identifiers through generation, buffering, and delivery to understand which state changes when the communication link changes.
