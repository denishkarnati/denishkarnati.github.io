01 / MY CONTRIBUTION

Problem

I developed a patient-monitoring project that joined sensor acquisition on a BeagleBone Black with MQTT-based cloud communication. The work ran July–September 2023.

Constraint

An embedded Linux sensing path crosses several boundaries: the target image, device interfaces, sensor reads, and delivery to a remote consumer. A successful message alone does not establish correct sensor values or a reproducible target configuration.

Decision

I used Yocto Linux on the BeagleBone Black and integrated MAX30100 and LM35 sensors. I connected the acquired data to an MQTT communication path so that acquisition and remote delivery could be considered separately.

Result

I built an embedded Linux monitoring system with sensor integration and cloud messaging. My documented contribution is the target sensing and MQTT communication path.

Execution model

Embedded Linux built with Yocto, with target-side acquisition and MQTT communication. Linux provides the platform for the sensing application and network stack.

Toolchain & bench

Yocto, BeagleBone Black, MAX30100, LM35, C / Python project context, and MQTT.

04 / ENGINEERING REVIEW

Debugging approach

The useful inspection sequence is target configuration, raw sensor acquisition, message payload, then remote reception. It separates an unavailable sensor from an unavailable message path.

Trade-offs and next improvements

Image versus application

A reproducible Linux image and a correct sensing application need separate checks.

Messaging versus persistence

Delivery policy, offline buffering, and consumer duplicate handling must be defined before calling a path reliable.

Next evidence

A public Yocto layer or reproducible image manifest, plus a captured sample payload, would make the setup easier to reproduce.
