01 / PROJECT CONTEXT

What I worked on

Two applications of connected firmware

I built an IoT switch system using ESP8266 and MQTT, with remote control through web and mobile interfaces. In a separate smart-agriculture project, I used Arduino Uno, ESP8266, PIR sensing, and ultrasonic sensing for a crop-protection prototype.

The projects share a simple embedded pattern: obtain an input, represent it in software, communicate when needed, and change or report a device state. Their application goals differ, so they are described separately rather than presented as one deployed product.

The remote-switch path

The switch project connects a user-facing command to a microcontroller through MQTT. A useful explanation follows the message from the interface to the communication path and then to the embedded output. That makes it easier to discuss command state and device state without treating them as the same thing.

The interactive example below turns that distinction into visible behavior. An ON command changes a simulated GPIO output when the broker is available. With the link offline, a new command is rejected and the displayed output remains unchanged.

Model boundaries

Local command/acknowledgment teaching model with synthetic latency. Retained commands represent the latest requested state. No mains switching, real device, or network connection is controlled.

Try these experiments

  1. Send ON, disconnect Wi-Fi, then send OFF with retained commands enabled.
  2. Reconnect Wi-Fi and inspect desired state, device output, and acknowledgment.
  3. Drop an ACK or send an invalid payload; use Query device to reconcile reported state.
04 / ENGINEERING NOTES

Decisions worth making explicit.

BoundaryWhy it mattersWhat to inspect
Desired vs reported state

A successful publish should not be confused with a confirmed physical output.

Track a command ID, pending state, device application, and acknowledgment.

Reconnect policy

A device returning after an outage needs a clear policy for the latest desired state.

Compare retained and non-retained commands in the model.

Input validation

A connected interface should not turn an arbitrary payload into an output change.

Reject malformed commands and keep the previous output unchanged.
