01 / MY CONTRIBUTION

Problem

I built connected-device projects that translated remote commands and sensor inputs into microcontroller behavior: an ESP8266 / MQTT switching system and an Arduino-based crop-protection prototype.

Constraint

A network command and a physical device action are separate events. Sensing also needs to distinguish the observed input from the action taken in response. Those boundaries matter when connectivity fails or a sensor changes state.

Decision

For remote switching, I developed an IoT system supporting web and mobile control with ESP8266 and MQTT. For crop protection, I integrated PIR and ultrasonic sensors with Arduino Uno / ESP8266 hardware for intrusion monitoring.

Result

The remote-switching project ran January–April 2021. The crop-protection prototype ran June–September 2020. I developed the connected control and sensing behavior across the microcontroller and communication interfaces.

Execution model

Microcontroller firmware on ESP8266 and Arduino Uno platforms, with Wi-Fi / MQTT for connected control and sensor-driven behavior.

Toolchain & bench

Embedded C/C++ project context, ESP8266, Arduino Uno, MQTT, PIR sensing, and ultrasonic sensing.

04 / ENGINEERING REVIEW

Debugging approach

Inspect command reception, device state, and the physical interface separately. For sensing, compare the raw input condition with the decision that triggers an output; for switching, distinguish desired state from observed device state.

Trade-offs and next improvements

Command versus confirmation

A publish operation does not by itself prove that the device changed its output.

Connectivity policy

Reconnect behavior and retained-message policy should be explicit before a connected switch is treated as predictable.

Next evidence

A bench recording and a small public firmware example would make the command-to-output behavior reviewable.
