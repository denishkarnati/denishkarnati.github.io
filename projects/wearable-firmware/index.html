01 / MY CONTRIBUTION

Problem

A wearable data path has to connect sensor acquisition, device firmware, wireless delivery, and host-side inspection. I developed the C/C++ firmware and Python tools that connect those boundaries at Texas A&M’s Optical Bio-Sensing Laboratory.

Constraint

Sampling and BLE delivery run on different schedules. A live plot alone cannot identify whether a problem begins at the sensor, the bus transaction, firmware timing, or host decoding. The system also needs device identification, battery telemetry, and useful access during board bring-up.

Decision

I implemented interrupt-driven multichannel acquisition in Zephyr and BLE GATT streaming on nRF52840 / nRF52832 targets. I integrated ADC, temperature, inertial, and power-management devices over SPI, I2C, and GPIO. This keeps acquisition and the host communication path explicit rather than treating the plotted signal as the whole system.

Result

I built a device-to-host workflow with BLE discovery, device selection, live plots, battery monitoring, CSV logging, and automated collection. I used PySide6, pyqtgraph, and Bleak for the host tools. My contribution covered firmware, sensor integration, custom-board bring-up, and the software used to inspect acquired data.

Execution model & tools +

Execution model

Zephyr RTOS with interrupt-driven acquisition and firmware threads; BLE GATT transports data to a Python host. The execution model separates acquisition events from application and host work.

Toolchain & bench

C/C++, nRF Connect SDK, Zephyr, SEGGER RTT, oscilloscopes, logic analyzers, multimeters; Python, PySide6, pyqtgraph, and Bleak.

04 / ENGINEERING REVIEW

Debugging approach

I isolated timing, communication, power-rail, ADC, and sensor-interface faults during custom-PCB bring-up. The useful investigation boundary is the raw interface: compare bus activity and firmware observations before interpreting host plots.

Trade-offs and next improvements

Timing versus delivery

A timestamp at the host describes arrival, not necessarily acquisition. Keep a sample sequence and acquisition time visible when measuring an actual device.

Buffering versus latency

A larger buffer can postpone loss while increasing data age. The illustration exposes that trade-off.

Next evidence

The desktop capture shows the live host tool. A reproducible measurement report would additionally record the firmware revision, acquisition settings, and capture conditions.
